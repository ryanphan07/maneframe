# Session 34

## Export loudness (hoco_40s, 6 to 7 spoken quips per engine)

Defaults: `EXPORT_QUIP_LUFS` -14, `EXPORT_DUCK_DB` -14; each quip goes through `acompressor` then `loudnorm`. Method differs from session 33's correlation fit: the ducked original is rebuilt from the source with the filter's gain, and the commentary is the exported audio minus that bed, over each quip's window (mono, 48 kHz). Mix level is RMS over the quip window.

| | before (session 33, -10 dB duck, no normalization) edge / piper | after edge | after piper |
|---|---|---|---|
| Commentary above ducked original, mean | +2.0 / +7.4 dB | +13.8 dB | +14.4 dB |
| Commentary above ducked original, worst quip | +1 to +4 dB (edge) / n.a. | +12.3 dB | +11.6 dB |
| Mix in quip window vs 1.5 s before | -2.4 / +0.2 dB | +1.8 dB | +0.5 dB |
| Mix in quip window vs the unducked source in that window | n.a. | -0.6 dB | +0.1 dB |

Steps that did not work, for the record: `loudnorm` alone (single pass, -16 and -14) left piper quips between -14.5 and -21.4 LUFS (worst quip only +6.6 dB above the bed) because piper clips are peaky (0 dBTP at about -20 LUFS) and loudnorm cannot raise them without clipping; a two-pass linear `loudnorm` was no better for the same reason and was dropped. Compressing first (threshold -24 dB, ratio 3) brought the quips to within 2.5 dB of each other. Raising the target to -12 or -10 LUFS gains under 1 dB.

The ducked bed stays audible (14 dB down), so the clip keeps its atmosphere; `EXPORT_DUCK_DB` sets how far it is lowered.

## Warm start (`start.ps1` sends one tiny chat request after llama-server is healthy)

The request (`max_tokens` 1, text only) takes 2.3 s on a cold server. First partial quip on hoco_40s, 35B, edge:

| Run | First partial | Window 1 | Later windows |
|---|---|---|---|
| Cold, normal speed (first run) | 61.1 s | 55.2 s | about 50 s |
| Cold, slow-GPU period (later run) | 131.0 s | 119.9 s | 92 to 96 s |
| After the warm-up request (last run) | 56.5 s | 45.7 s | not recorded |

The GPU speed on this machine drifted by 2 to 3x between runs (not caused by this app; another load on the machine is the likely reason), so the comparison is not clean. Within one run the first window is 10 to 25% slower than the later ones when cold, and the warm-up request removes that: expect a 5 to 15 s saving on a normal day. A text-only request does not warm the image encoder, but window 1 was faster than the cold runs, so the weights load was the main cost.

## Other findings

- Running `pytest` while the backend is serving a job deletes that job's upload: several tests start the app with the real upload folder and the startup sweep removes leftovers (seen as "Error opening video file" in the live job). Test isolation issue, not fixed; do not run the tests during a live job.
- H.264 clips are never transcoded, so a 4K 120 fps H.264 upload keeps its size and frame rate through analysis and export (untested).
